LM-kT in flashjet:
an opt-in, IRC-safe learned pair metric for clustering

Why the clustering hook belongs in the library and the network does not

Chirayu Gupta · 2026-11-10 · revision r1

Internal. All results are from our own Pythia 8 samples at truth level (13.6 TeV) plus JetClass (Delphes) for the tagger check; private work, not CMS-approved. Results are from Sept 2026 studies and have not been independently reviewed.

Summary

  • Proposal: add cluster_lmkt to flashjet as an experimental, opt-in clustering with an external pair matrix G. The network that produces G stays out of the library.
  • What it does: generalised kT with a bounded learned factor on the pair distance, dab = ΔR²ab · exp(clip(gab, ±c)).
  • Why bother: for top jets it pairs the two W quarks correctly 0.66 of the time, vs 0.33 for C/A, closing ~60% of the gap to a truth oracle (0.86).
  • Safe to add:
    • G = 0 or c = 0 reproduces anti-kt, C/A and kt bit for bit (pinned in tests); existing users see no change
    • IRC failure rate equal to C/A on real jets; QCD not sculpted (fake W 0.096 vs 0.108)
    • 22 LM-kT tests pass, including a brute-force check of the definition
  • Honest limits: small tagging gain (+0.5 pt accuracy on JetClass), torch-only today (≈160× slower than Triton C/A), model-dependent jet definition if G comes from a network.
  • Prerequisite: land the _pseudojet_p4 padding fix on main first; it affects every user today.

Motivation: geometric trees get the hierarchy wrong

The problem

  • In a boosted top, t → b W → b q q′. C/A clusters by angle only, so it often merges b with one W quark first.
  • C/A pairs the W quarks correctly in only 33% of top jets, kt in 40%.
  • Any substructure built on the tree (W candidate mass, Lund plane, prong features) inherits this.

Why the tree is the right object

  • ParT's learned pair bias is, to ~77% (AUC recovery), a function of the pair's C/A common-ancestor node.
  • So taggers already use tree-like pair information; a better tree is a compact, IRC-safe way to supply it.

Why in flashjet

  • flashjet is where the trees are built (batched GPU clustering, history decode, grooming, Lund coordinates).
  • A learned metric is a small change to the distance, not a new library: same merge loop, same history schema.
  • Users can plug in LM-kT's GNN or any other learned pair score, without flashjet shipping a model.
"Same answer as FastJet, faster" stays the default. Learned clustering is a flag you turn on.

The algorithm (LM-kT)

Inputs

  • Constituents pi, mask, (R, p) as usual.
  • Pair matrix Gij (B×N×N, symmetric). Negative = pull together, positive = push apart.

Merge loop (n−1 steps)

  • gab = Lab / (SaSb): the pT-weighted average of G over a × b, with S = ΣpT, Lab = Σ pTipTjGij.
  • dab = ΔR²ab · exp(clip(gab, −c, c)) (C/A; general p via kt2p). c = 4: factor in [1/55, 55].
  • On merge: L row of the new pseudojet = La + Lb. Exact, O(n) per merge.
  • Options: zmin (modulate only hard pairs), geo=False (distance from G only, with a collinear guard), beam (inclusive vs one tree per jet).

Why it is IRC safe

  • Collinear: ΔR = 0 gives d = 0 for any bounded g, so collinear pieces merge first, and their pT-weighted rows sum to the unsplit particle's row.
  • Infrared: a soft particle enters every average with weight pT → 0, and the factor is bounded.
  • G itself comes from an energy-weighted GNN (pT only as attention weight), so G is IRC safe too.

Masses and QCD: no sculpting

  • Top W candidate: sharper peak at mW, smaller low-mass shoulder than C/A.
  • QCD: fake W rate (groomed 2-prong mass 65–105 GeV) 0.096 vs 0.108 for C/A; kt sculpts badly (0.274).
  • W mass window (±15%): 0.78 vs 0.82 for C/A. Soft particles get learned nudges into prongs, giving a high-mass tail.
  • Fix in the code: zmin, apply the factor only to pairs with z > zmin (IRC safe like a Soft Drop cut). Not yet evaluated.

What it costs, and what it does not buy

Speed (T4, 512 jets × 128 particles)

steptime
GNN forward (makes G)534 ms
LM-kT torch, c = 4639 ms
flashjet torch backend, C/A643 ms
flashjet Triton, C/A4.0 ms
  • LM-kT runs at torch-backend speed today. Triton speed needs the modulation (and the O(n) row update) in the kernel.
  • The GNN is ~130× the fused clustering; a distilled student is the plan for inference.

Tagging gain is modest

  • JetClass, BDT on tree features: acc 0.708 (LM-kT) vs 0.704 (C/A), ±0.2 stat; the gain sits in top and Hbb.
  • Substituting ParT's pair bias by a function of the tree: LM-kT recovers 72%, C/A 77%.

Open problems

  • GNN trained on pairs, not merges: pair AUC 0.999 becomes 0.88 in the tree.
  • Trained on our truth-level Pythia, applied to Delphes without retraining: a G from a network makes the jet definition model-dependent.
So: the case is substructure (finding the W inside a top, prong assignment), not a generic tagging boost. That is why it should be an opt-in hook, not a default.

Later, if there is a use case that needs it

  • Learned factor in the Triton kernel, plus a distilled small network for G, to keep flashjet speed.

  • Same hook enables cheap follow-ups: wider envelopes (R = 1.2–1.5) and the radius-free geo=False mode (never evaluated so far).

The ask: accept a small, tested, opt-in distance hook in flashjet core. It costs nothing when off, and gives a clean place to test learned clustering at scale.

Pair-level view

  • zizj-weighted same-prong AUC over labelled pairs, signal jets. Trees scored by the merge step at which a pair first shares a pseudojet (lowest common ancestor).
  • GNN logit 0.999 vs ΔR alone 0.983; in the tree LM-kT c=4 gives 0.882 vs C/A 0.869.
  • Anti-kt scores 0.913 here, likely because its pT-ordered merging keeps soft particles separate until late; this metric rewards ordering inside prongs, not the prong hierarchy that the tree-quality metrics measure.
  • The drop from 0.999 to 0.88 is the "trained on pairs, not merges" gap.
