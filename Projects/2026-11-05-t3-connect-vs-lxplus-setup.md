This could matter for code-heavy HToWW/Flashjet/DigiMorphing work. The improvement is an inference; no timing or reliability benchmark was run. Model response latency and CERN storage latency remain.
2. **SSH is already integrated with this laptop.** Reusing that path avoids adding a managed cloud tunnel just to obtain remote execution. However, T3's launcher has not been tested with this alias, ControlMaster, BatchMode or authentication helper. A service is helpful plumbing, not proof of compatibility.
3. **lxplus suitability remains a gate.** A persistent T3 server/provider process, its credential access and any outbound tunnel need CERN clearance. Moving the master into a laptop service does not resolve these remote-host questions.
4. **The current research-record workflow is valuable.** Keep conductor/keeper and Obsidian on the laptop, one worker globally, and one reviewed path for bringing worker commits into the vault. Migration across all projects now would add coordination work before the benefit is measured.

**What T3 actually changes — documentation verified, deployment unverified**

An environment owns the T3 server, provider/agent processes, terminals, Git operations, files and durable conversation state. Its projects bind to directories on that machine; threads belong to that environment and use their selected workspace/worktree. Similar repository identities can group checkouts across machines without synchronizing files or moving existing threads. A project name is not a container or a separate CERN identity. [T3 v0.1.6 architecture](https://github.com/pingdotgg/t3code/blob/v0.1.6/docs/internals/remote.md)

Provider installation, login and configuration belong on the environment's host. Thus remote execution would require an approved provider setup on lxplus; the laptop's model login is not automatically forwarded. Model requests still leave for the configured inference service. Running the agent at CERN does not establish that inference stays at CERN. [Provider setup](https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md#providers)

Desktop **Add environment → SSH** starts/reuses T3 remotely and forwards its endpoint. Initial setup downloads a runtime. Connect instead uses account sign-in, a browser link/code confirmation, and host exposure; `t3 connect`/`t3 up --connect` set that up. Direct pairing exchanges a one-time code for a session. Connect documents limits of **3 machines**, **10 with Pro**, **100 with Premier**; projects are not machine slots. `t3 connect unlink` disables exposure; logout also removes login. Deregistration revokes cloud access; forgetting a device entry alone does not. [Version-matched remote guide](https://github.com/pingdotgg/t3code/blob/v0.1.6/docs/user/remote-access.md)

Agent-to-environment **peer linking** is another authorization: both servers enable its beta, and the receiving server grants an MCP session. It is unnecessary for Chirayu to select a remote environment himself. Unlinking locally forgets that credential; revoke it on the receiving server to end its authority. A full-access link is not an OS isolation boundary. [Peer-link architecture](https://github.com/pingdotgg/t3code/blob/v0.1.6/docs/internals/remote.md#peer-links)

T3 Connect uses Clerk identity and managed Cloudflare tunnels. Its broker is part of the trust boundary; this is not evidence of CERN acceptance or a guarantee that intermediaries cannot access content. Avoid offline webhook storage and other unrelated cloud features in a pilot. [Connect architecture](https://github.com/pingdotgg/t3code/blob/v0.1.6/docs/internals/t3-connect.md)

The host connector needs outbound Cloudflare port **7844** for QUIC/HTTP2, plus connectivity for sign-in, downloads and model services. DNS/TLS problems, blocked tunnels, expired sign-ins, clock skew, host downtime, limits and client/server incompatibility can break access. These requirements were checked in documentation, not tested from CERN. [Troubleshooting](https://github.com/pingdotgg/t3code/blob/main/docs/user/t3-connect-troubleshooting.md)

**What improves, and what can still break**

- **Latency/mounts:** remote tools avoid SSHFS metadata round trips and laptop FUSE failures. A warm master already avoids repeated SSH authentication, so the shell-only gain may be modest. AFS/EOS remain network filesystems on lxplus. Disconnecting a UI need not stop a remote process, but host/session survival must be established separately.
- **Permissions/prompts:** CERN access remains that of the account running the process. T3's thread permission mode and provider sandbox remain additional controls. Remote placement may avoid laptop sandbox restrictions on mount paths; it does not promise fewer prompts. Do not select Full access merely to remove them. [Permission modes](https://github.com/pingdotgg/t3code/blob/main/docs/user/permission-modes.md)
- **Kerberos/AFS:** a server started as a service may not inherit the interactive session's credential cache or AFS authorization context. A living process or open SSH socket is not proof of a valid ticket. Re-login elsewhere may not update the daemon's credentials. CERN documentation describes GSSAPI/delegation and DNS-alias pitfalls; no live ticket state was checked. [CERN Kerberos guide](https://linux.web.cern.ch/docs/kerberos-access/)
- **Proxy/CMSSW/CRAB/Condor:** local invocation simplifies paths and shell quoting, but still needs the correct release, shell setup, scheduler configuration and credentials. A proxy in one node's `/tmp` is not automatically present after reconnecting to another node; an explicit proxy path also has expiry/access requirements. CRAB can manage remote credentials even during commands that appear informational, so initial checks should be offline. CERN's public CRAB FAQ documents proxy and environment dependencies, but contains legacy-release guidance; it is not validation of today's setup. [CRAB FAQ](https://twiki.cern.ch/twiki/bin/view/CMSPublic/CRAB3FAQ). Submission/resubmission/removal remain separately authorized actions.
- **Host/state:** `lxplus.cern.ch` can land on another node. Shared home files do not move a process, its port or node-local credentials. Avoid multiple servers using one T3 state directory from different nodes. T3's SQLite/state, logs, runtimes and worktrees also need suitable filesystem locking and quota. AFS/EOS suitability for T3's live database was not verified.
