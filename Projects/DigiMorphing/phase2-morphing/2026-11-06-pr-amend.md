## forthommel's ~20% step-3 CPU question

**Profiling inputs.** I read the public Circles JSONs (`https://cmssdt.cern.ch/circles/web/profiling/CMSSW_20_1_X_<IB>/el9_amd64_gcc14/38434.21/[PR-…/]step3_cpu.resources.json`) on 2026-11-06. Local copies are in `/tmp/prof_data`, and the script is `/tmp/prof_scripts/cmp.py`. Each file covers 10 events, and the times below are summed module `time_thread`.

| step3, wf 38434.21 | thread time (s) |
|---|---|
| IB 2026-11-01-2300 | 36.10 |
| **this PR (PR-708f10/57119)** | **42.85** |
| unrelated PR-280cbc/57113, same IB | 44.45 |
| unrelated PR-e3b333/57117, same IB | 43.71 |
| other IB baselines, 11-01-0000 … 11-05-2300 (no PR) | 34.96 – 48.72 |

**Findings:**
- Step 3 of the profiled workflow (38434.21) **does not run `SiPixelPhase2DigiToCluster` or any SiPixel Alpaka module**. Pixel clustering there is the legacy CPU `SiPixelClusterProducer`, which this PR does not touch, so the PR's code is not executed in that step.
- The increase is spread across everything. The largest share is the "other" category (+5.2 s). Unrelated modules such as `AODSIMoutput`, `lowPtGsfElectronSeeds`, `muons1stStep` and `ecalMultiFitUncalibRecHit` also rise, and so does the legacy `siPixelClusters`, by 98 → 130 ms.
- Two unrelated PRs tested on the same IB show the same rise, and the IB-to-IB spread with no PR is about ±20%. This points to machine or load noise, not this PR.

**HLT timing server.** Chirayu's Google Slides deck "Timing Performance (Phase-2 HLT)" (read via its public txt export) ran PR #52363 code with morphing on in BPIX L1. Setup: 1000 TTbar PU200 events, D110, CMSSW_17_0_0_pre7, 2×EPYC 7763 + 2×T4.

| Round 5 (3 repetitions) | ms/event | events/s |
|---|---|---|
| morphing disabled | 5152.8 ± 6.5 | 38.0 ± 0.1 |
| morphing enabled | 5160.3 ± 3.9 | 38.0 ± 0.1 |

The deck's conclusion is that there is no measurable cost. GPU out-of-memory crashes in the first repetition occurred with morphing disabled only and are attributed to cold start, not to morphing.
